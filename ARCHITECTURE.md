# Axiusflow Architecture

## Product

Axiusflow is a local-first professional trading platform in the category of MotiveWave and ATAS. It is a native Rust desktop application for live market data, charting, market-depth workflows, local history, and eventually safe trade execution.

The product target is best-in-class interactive and streaming performance without becoming a heavyweight workstation. Architecture is a product advantage: low latency, predictable resource use, immediate local startup, strong failure isolation, and simple ownership should distinguish Axiusflow from existing platforms.

This document describes the current architectural direction. Source code, tests, and measured runtime behavior are the implementation truth.

## Principles

1. Local only. Core viewing, history, provider connectivity, and workspace behavior run on the user's machine and have no remote Axiusflow service dependency.
2. Correct before fast. Market data, sequence handling, history/live handoff, prices, quantities, and future orders must remain exact under disconnects, retries, and restarts.
3. Measure performance. Optimize observed hot paths and tail latency. Do not add speculative caches, concurrency, unsafe code, or platform-specific acceleration.
4. Keep ownership obvious. Each mutable resource has one clear owner. Communication across threads and processes uses bounded messages and explicit snapshots or deltas.
5. Stay lightweight. Prefer Rust and the standard library, operating-system facilities, and dependencies already in the workspace. New layers and dependencies require a present need.
6. Preserve the native experience. Windows, macOS, and Linux behavior should follow each operating system's conventions. Native windowing, credential storage, power, network, and display facilities belong behind narrow platform boundaries.
7. Fail safely. Stale generations, gaps, malformed provider data, unavailable credentials, and interrupted persistence must produce explicit recovery or errors, never plausible but incorrect trading state.

## Runtime topology

Axiusflow ships two local application processes:

- `axiusflow_desktop` owns the GPUI window, terminal interaction, presentation state, chart integration, lifecycle coordination, and bounded background engine-client bridges. It no longer links the resident engine server application as a library and creates no Coinbase or Rithmic provider session, history connection, credential-vault access, native provider lifecycle monitor, or market-data storage path.
- `axiusflow_engine` is the per-user resident local process. It owns authenticated workspace/watchlist/viewport/hot-set persistence and the current production market slice: one bounded market coordinator, separate bounded Coinbase and Rithmic history workers, shared Coinbase and Rithmic realtime workers, one engine-owned Rithmic catalog/quote session, one encrypted provider-neutral local-history worker, a bounded provider-neutral selected-instrument catalog, canonical in-memory Coinbase and Rithmic bars, one authoritative bounded Rithmic order book, and per-consumer IPC snapshots. Coinbase and Rithmic bar history are engine-owned and survive restart. All Rithmic provider credentials, catalog discovery, selection installation, replay planning, cancellation, canonical collection for all 15 supported chart cadences, persistence, transport retry, native power/network transitions, live tick/fixed/session/calendar candle continuation, depth continuity/reconstruction, and publication are engine-owned. The engine accepts authenticated operational resource-mode, durable lifetime/autostart/markets-live preference, status, and complete-shutdown commands. `axiusflow_engine --shutdown` and the shared desktop lifecycle helper connect to an existing engine without starting another. After authentication the server freezes persistent workspace mutation, closes its listener, concurrently writes a newer revisioned hot-set manifest, cancels in-flight history and Coinbase realtime work, disconnects Rithmic control channels so active provider runtimes stop, drains already-accepted local-history requests, and joins the coordinator plus its top-level provider/history/storage workers within one shared two-second process deadline. Each Rithmic catalog/realtime worker retains cancellable native network/power wait handles and joins both named monitor helpers before it can finish. A flush, worker, or client-session failure produces a diagnostic and nonzero process exit. Hot-set publication retains only the latest two manifests, so a prior equal-revision viewport manifest cannot overwrite a newer selection on restart. Optional per-user autostart uses Windows HKCU Run, Linux XDG autostart, or a macOS LaunchAgent through one platform boundary. Native system/session shutdown requests the same bounded engine shutdown through Windows session-end messages, Linux logind plus termination signals, or macOS launch/session termination signals. Default desktop close keeps the established engine warm and releases unused Coinbase realtime work; the persisted markets-live mode retains bounded selected handoffs and provider sessions after the last UI client detaches, while Exit Completely performs complete shutdown.

The default shipping desktop starts bounded background `EngineClient` support and sends generation-fenced demand over protocol v13. A desktop-owned `EngineSupervisor` reconnects after engine loss and restores current clients, consumers, provider-neutral selections, demands, viewports, and resource classes in generation order. One coordinator thread multiplexes chart endpoints through one authenticated connection; Rithmic presentation uses provider-neutral IPC and never a provider socket. Provider history, realtime handoff, canonical validation, aggregation, memory installation, persistence, publication, and IPC remain engine-owned and bounded. EOF or framing failure detaches the complete client-owned demand set. The desktop validates publications into independent application models and applies them to Nucleus only on GPUI frame boundaries.

The normal launch opens one chart and `--multi-chart` retains the separate-window proof. `--workspace-tabs` now opens one GPUI application shell whose persisted, revision-fenced tab list contains bounded native Nucleus split trees. Each chart pane owns stable workspace, pane, and consumer identities plus isolated presentation state; tab creation, activation, reorder, close, native pane split, native divider resize, pane close, and deterministic restore mutate the existing shell without creating provider sessions, databases, runtimes, or engine instances. Schema 5 persists the recursive split direction and ratio at each tree node while retaining schema-4 flat geometry only for migration. The active workspace's panes are foreground; hidden open tabs are background, recent/pinned retained identities may be warm, and closed panes become detached. Only foreground mailboxes accept UI market publications. Class transitions use a bounded latest-value slot, discard stale hidden UI publications, and receive a newer covering snapshot before incremental display resumes. Hidden panes do not poll or render continuously, while shared engine demand keeps exact canonical series and upstream subscriptions coalesced. Layout persistence is debounced off GPUI through one bounded latest-value writer. Fullscreen removes the title/tab bar while preserving active chart controls and panes.

```text
GPUI demand
    -> bounded desktop EngineClient worker
    -> authenticated protocol-v13 local IPC
    -> resident MarketEngine coordinator
    -> Coinbase public-history worker + Coinbase realtime worker
    -> canonical fixed-point bars and bounded SeriesStore
    -> bounded per-consumer IPC state/snapshot/tail publication
    -> desktop application model and frame-conflated bounded UI mailbox
    -> terminal UI and Nucleus chart renderer
```

Rithmic live continuation covers all 15 supported cadences. The Rithmic adapter owns CME-family Chicago session-roll and daylight-saving calendar buckets for 1W/1M history and live trades, while the engine carries the completed daily replay end watermark into the live handoff so buffered trades already represented in history cannot be applied twice.

## Workspace boundaries

### Applications

- `apps/desktop`: native GPUI application, window chrome, terminal composition, UI event routing, desktop diagnostics, and its app-local bounded market-presentation mailbox plus deterministic disconnected fixture.
- `apps/engine`: resident engine executable plus authenticated local IPC, activation, workspace persistence, recovery, migration, and corrupt-file quarantine.

### Domain and application

- `crates/domain/instruments`: provider-neutral instrument identity.
- `crates/domain/market_data`: canonical bars, intervals, order-book state, and related market semantics.
- `crates/application`: generation-aware client models, provenance validation, replay snapshots, embedded deterministic replay input, transport-neutral replay checksums and sequence mechanics, and other provider-neutral pure state. It owns no worker, queue, socket, storage, or runtime lifecycle.
- `crates/market_engine`: headless engine core with one explicitly owned demand registry, shared subscription registry, provider-session manager, bounded canonical series store, monotonic per-consumer publication manager, bounded provider-neutral order-flow reconstruction, hot-set ranking, and deterministic resource-policy calculation. Demand records include generation, exact canonical series identity, viewport, foreground/background/warm/detached class, and bars/trades/quotes/depth requirements. The hot set ranks active-workspace membership, watchlists, pins, and recency under explicit memory capacity; active and pinned entries outrank evictable recency-only entries. The order-flow owner publishes bounded view-ready bid/ask levels, delta, cumulative delta, volume profile inputs, and tape snapshots/deltas, and atomically reconstructs bounded historical trades. `apps/engine` drives the core on one coordinator thread; the core remains free of provider adapters, storage, IPC, GPUI, threads, and globals.

These crates must not depend on UI or a particular provider.

### Providers and coordination

- `crates/adapters/coinbase_market`: Coinbase catalog, history, streaming, and wire behavior.
- `crates/adapters/rithmic_protocol`: Rithmic protocol, network sessions, provider lifecycle and generation fencing, session contracts, catalog, history, and market-data behavior. It owns canonical collection and exact timestamp conversion for all 15 supported chart cadences, including daily-session aggregation into calendar weeks and months. Its lifecycle writes directly into the bounded feed accumulator owned by `observability`; there is no intermediate diagnostics wrapper.
- `crates/provider_history`: provider-neutral pagination, rate limiting, coverage, scheduling, and history/live handoff.

Provider-specific types stop at adapter boundaries. Downstream code consumes canonical identities and market models.

### Local data and protocols

- `crates/local_storage`: SQLite metadata, encrypted local segments, and storage lifecycle.
- `crates/local_history`: engine-consumed, provider-neutral local bar-history mechanics built on `local_storage`: native-vault key access, encrypted immutable segment publication, exact retained reads, current/legacy schema decoding, and canonical validation. It owns no provider repair, generation, live-handoff, chart, or GPUI behavior.
- `crates/local_engine_client`: blocking authenticated local-IPC client, native installation-token access, sibling-engine discovery/startup, framing, typed workspace/market/lifecycle/status commands, bounded consumer-aware market-response realignment, and complete engine shutdown. It contains no provider, market-state, storage, or GPUI behavior. Desktop supervisors call its blocking connection/start APIs only from background workers; the resident engine reuses its installation-token access and authenticated client for the explicit `--shutdown` lifecycle action.
- `crates/engine_protocol`: versioned authentication, workspace, lifecycle, engine market-demand, readiness, provider state, provider-neutral catalog selection, fixed-point series/order-book/order-flow publication, and staged errors. Its product-level command surface includes revision-fenced complete tab/pane layouts and exact consumer resource classes; it exposes no provider wire messages, storage operations, scheduler state, locks, or worker handles. Protocol version 13 carries stable workspace/pane/consumer identities, recursive native split geometry, full canonical series identity, order-flow snapshots/deltas, structured failure stage/category/cause/elapsed context, generation/provenance/precision contracts, and the enlarged bounded frame required by one maximum working-window snapshot. The protocol-derived endpoint name plus strict negotiation prevents an incompatible resident engine from being reused.
- `crates/transport`: shared bounded length-prefixed framing used by the local engine protocol.

Persistent writes use revisioned or transactional publication so a crash cannot turn a partial write into current state. Credentials and sensitive provider material must use the native credential vault or zeroizing memory, not source files, logs, or plain-text configuration.

## Local market-data execution

The default implemented Coinbase path is:

```text
GPUI demand
    -> desktop EngineClient worker
    -> authenticated local IPC
    -> engine MarketEngine coordinator
    -> Coinbase history worker + realtime WebSocket worker
    -> canonical completed bars + active-candle aggregation
    -> bounded shared SeriesStore
    -> bounded fixed-point IPC snapshots and explicit provider state
    -> desktop validation and bounded mailbox
    -> chart bridge and Nucleus Charts
```

The production market path supports every active Coinbase spot product installed from the engine-owned catalog. Coinbase supports live fixed bars from 1m through 1D and history-only 1W/1M series, plus the provider-neutral Rithmic cadence/catalog/depth path. Coinbase catalog authorization and completed search state are generation-fenced, bounded by the 256 registered-consumer limit, and synchronously retired when a consumer is removed or its client detaches. Every Coinbase catalog worker event carries the authorization generation that produced it, and the coordinator revalidates that generation before installing an instrument or publishing a result, so queued stale work cannot regain resident authority after detach or consumer reuse. The coordinator derives product identity and precision from the installed instrument, and the realtime worker owns the exact sorted demanded-product subscription set under Coinbase's 64-product bound. It reconnects only when that product set changes and cooperatively cancels history owned by superseded provider generations; switching cadence on the same product preserves the provider generation. One bounded engine storage worker owns the authenticated catalog and encrypted immutable segments; exact hot memory, compatible finer memory, retained derived/native history, and provider repair are queried in that order. Completed history is immutable and shared separately from the forming tail. Provider generations, account/instrument/entitlement/cadence identity, fixed-point precision, nanosecond ordering, snapshot/delta continuity, history/live handoff, and persistence degradation remain independently fenced. One process-owned provider session serves shared accepted demand and is released only after the final subscription reference unless explicit Markets Live retention owns it. Protocol v13 publishes bars, top-20 canonical DOM, and bounded view-ready order-flow snapshots/deltas; the desktop formats and renders those canonical images without reconstructing provider state. No shipping desktop path owns a provider connection.

Warm reconstruction is driven by a bounded provider-neutral hot set that records active workspace membership, watchlists, pins, recency, exact provider/account/instrument/entitlement/cadence identity, precision, viewport, retained coverage, and provider/series watermarks. Deterministic ranking assigns HOT to active-workspace demand, WARM to remaining ranked entries within the explicit memory capacity, and COLD to overflow; pins cannot be displaced by ordinary recency, while recency-only entries remain warm when capacity permits. Startup preloads available local history before desktop attachment and queues repair for missing coverage. Provider repair preserves accepted sequence IDs and fails closed on interior drift.

The coordinator applies one deterministic resource decision from lifecycle mode, available memory, consumer resource classes, provider limits, and hot-set priority. Foreground receives UI publication and required realtime; background retains shared upstream demand without UI publication; warm retains bounded canonical memory without an upstream subscription; detached owns neither UI publication nor upstream demand. This decision bounds decoded bars, derived series, hidden-depth retention, provider history size, and warm lifetime. Visible demand and explicit Markets Live retention cannot be evicted by hidden or recency-only consumers.

`ProviderSessionDriver` is an adapter-local Rithmic lifecycle and deterministic-test boundary. Coinbase does not implement it: its production history and realtime sessions are owned directly by engine workers through the Coinbase adapter's venue-specific transports. `ProviderHistoryAdapter` remains the shared paginated-history boundary. Authentication, transport framing, provider limits, product/catalog translation, and provider-specific recovery remain inside the adapters; downstream history, storage, engine, and UI code consumes canonical identities and values. Provider adapter production manifests depend only on canonical market data, provider-history contracts, platform/observability primitives, and venue wire/network libraries; storage/history fixtures remain dev-only and neither adapter links UI.

The obsolete `desktop_market_runtime` workspace crate is deleted. Its only remaining behavior—the bounded presentation mailbox, application-model handoff, and deterministic disconnected fixture—now lives in the `axiusflow_desktop` package alongside its sole consumer and retains the same bounded conflation and recovery tests. The app-local `rithmic_engine_client` and `rithmic_engine_history` modules are engine-protocol presentation clients only: they forward bounded provider-neutral catalog and series demand, continuously poll canonical chart and order-book snapshots, convert them into application/presentation models, and cancel obsolete demand by removing their engine consumer. `apps/desktop` depends on no provider adapter, provider-history implementation, storage implementation, or `market_engine`; its Coinbase presentation catalog uses the same provider-neutral installed-instrument protocol descriptor as other engine publications. The app-local Rithmic shell and series browser contain presentation state only. No desktop layer loads credentials or creates provider sessions. `apps/engine/src/rithmic_history.rs` owns native-vault history credential loading, bounded replay planning, the authenticated history connection, all 15 cadence collection, explicit close, and exact-time publication; `apps/engine/src/rithmic_realtime.rs` owns one authenticated ticker-session worker that serializes catalog, trade, and depth work, including bounded transport retry and native power/network transitions. Provider adapters stop at venue authentication, sockets, wire parsing, catalog translation, venue continuity, rate limits, paging, and provider-specific canonical conversion. The chart and DOM bridges retain consumer-side stale and identity rejection as defense in depth, not as second market-state owners.

The obsolete Coinbase desktop provider driver, event bridge, deterministic session fixture, feature flag, and the entire `desktop_provider_runtime` crate are deleted. The surviving Rithmic lifecycle, generation fence, vault boundary, and session contract live with the Rithmic adapter and report state directly to the engine-owned caller. The adapter retains only bounded provider callback queues that are actually consumed, while `observability::FeedDiagnostics` owns the metrics accumulator directly. The old `application::stream_runtime` immutable-publication wrapper and unconsumed desktop event/publication queue are also deleted. The unused protobuf market-stream schema, generated-protocol crate, and conversion adapter are deleted; production desktop-to-engine publication has exactly one wire contract in `engine_protocol`. The deterministic disconnected benchmark fixture now submits replay snapshots and deltas directly to the same application model used by engine publications and owns no thread or wire protocol.

The path is local by construction. Provider credentials stay on the user's machine, provider traffic terminates in a local worker, and durable history is stored under the user's local data root. No remote Axiusflow service, licensing gateway, or network chart service exists in the product architecture.

## Historical data and restart behavior

`local_storage` stores authenticated immutable segments and a keyed SQLite catalog. Segment publication is stage, sync, link, catalog commit; interrupted or corrupt files are recovered or quarantined rather than admitted as valid history. Catalog rows record exact provider/account/entitlement, instrument, resolution, time range, and source/schema/calendar/adjustment/correction revisions.

`provider_history::CoverageSnapshot` merges complete, confirmed-empty, invalidated, and quarantined ranges, then returns only the missing or damaged repair ranges. Visible repairs outrank adjacent prefetch. The provider-history scheduler defines and tests the shared fairness, retry, interest, and continuation rules; the current engine Coinbase composition submits one source-aware page per active series at a time through its bounded provider lane and requeues a continuation only after that page completes.

The engine's bounded storage worker owns `local_history::LocalHistoryStore`, never GPUI. The crate reads and decrypts exact immutable segments, validates identity, nanosecond timestamps, OHLCV, and contiguous sequence, preserves the legacy Coinbase segment schema, and publishes new provider-neutral bar segments through `local_storage`. Provider/account scope and compatible Coinbase derivation remain coordinator policy. Decoded canonical history is installed once into `MarketEngine::SeriesStore`; there is no second chart cache or history/live handoff runtime in `local_history`. Live items remain buffered and generation-fenced by the engine coordinator until covering history establishes continuity.

The current storage format supports progressive recent-first reads because retained history is segmented and range-indexed. Coinbase chart viewport changes are first-class desktop-worker demand: the active selection generation is checked, the visible time range is aligned to the source interval, one visible window is prefetched behind the viewport, duplicate ranges are deduplicated, overlapping encrypted local segments are read before provider repair, local coverage is installed directly, and only missing ranges are sent to the provider. After an initial covering foreground snapshot, the coordinator also arms the same viewport-repair path for the bounded 32,768-bar working window, reserving 512 bars for the current live edge; provider pages remain capped at 350 source bars while the coverage planner fetches only missing ranges. Repair-inflight bookkeeping is separate from per-consumer active viewport ownership, so completing coverage does not make a still-visible range evictable. Coinbase viewport, seam, and interior-hole repairs merge real provider bars into the current covering image and atomically replace that image without invalidating the current forming tail; a failed seam repair does not resume live aggregation across the known gap. Local segment reads update last-viewed recency, and the encrypted cache reserves exact encrypted bytes before publication to enforce a hard 2 GiB physical segment budget. Quarantine files and then least-recently-viewed unprotected segments are removed first; current and readable legacy segments overlapping active viewport or live-edge ranges remain protected when a new publication fits, while a pre-existing over-budget store is brought back under the ceiling with explicit protected-data degradation. An empty Coinbase response records only that exact confirmed-empty range; adjacent markers coalesce, and later real bars remove overlapping empty evidence before cache reservation. If the bounded persistence lane is saturated, the coordinator retains one coalesced metadata repair per active series and retries it through the storage worker, so failed payload retention or queue pressure cannot turn repaired history into a durable hole after restart.

## Timeframes

Provider-native history is requested at the closest supported source resolution. The engine maps Coinbase's 1m, 3m, 5m, 15m, 30m, 1h, 2h, 4h, 8h, 12h, and 1D chart intervals to the adapter's source granularities and aggregates source candles where necessary; the same fixed interval is used for incremental live-trade aggregation. Coinbase 1W/1M history is aggregated from the daily source and publishes only completed calendar buckets because it has no live trade stream; desktop state explicitly reports that the current calendar bucket is not live. Rithmic maps canonical chart intervals to its provider bar specifications behind its adapter.

The durable identity includes resolution and source revision, so native and derived data cannot be confused. Coinbase warm switches first look for immutable derived chunks keyed by source revision and interval; when absent, retained canonical one-minute chunks are aggregated once, published immediately, and stored under the bounded derived-data quota before provider reconciliation. Rithmic retains its provider-native series mapping. Calendar intervals keep explicit UTC/exchange-calendar bucket rules instead of being approximated as fixed seconds.

## Concurrency model

- The resident market coordinator drives one headless `MarketEngine`, whose demand, shared subscription, provider-session, series, and publication components are the single mutable owners of their respective state.
- Each market command is authorized against the authenticated session's attached client identity; one desktop client cannot mutate another client's consumers.
- One bounded engine history worker owns the Coinbase history adapter; provider I/O never blocks GPUI or the market coordinator.
- One bounded engine realtime worker owns the Coinbase WebSocket. Its generation-fenced events enter a bounded queue; queue overflow, sequence invalidation, or disconnect forces explicit recovery and a covering history repair.
- The coordinator stores at most the latest provider state, snapshot, and series state per consumer. Covering snapshots may conflate; provider deltas are not silently discarded.
- The bounded desktop engine-client worker interleaves commands with 16 ms market-event polling and application-model conversion, never provider execution or canonical market state. A foreground mailbox edge wakes the terminal's bounded frame gate directly; it does not notify the workspace shell merely to schedule that poll.
- Coinbase chart endpoints are grouped behind one desktop engine-client thread and one authenticated connection; adding endpoints adds bounded consumer mailboxes, not desktop threads, runtimes, provider sockets, history managers, or storage workers. The Rithmic presentation path likewise owns one app-level engine client and one bounded history/result helper, independent of provider worker count.
- The engine owns separate bounded Rithmic catalog/quote, history, and realtime workers plus the authoritative bounded order book. Provider workers apply native power/network transitions before provider retry; the desktop Rithmic bridge owns only IPC polling and chart/DOM presentation projection.
- Blocking history and storage work stays off GPUI and communicates through bounded channels.
- Selection generations make obsolete symbol and timeframe results stale; stale work cannot overwrite the new selection.
- The desktop command boundary coalesces selection changes to the newest state until the bounded provider-worker mailbox accepts it; queue pressure must never silently discard the active selection.
- Chart viewport changes are also retained as demand on the active series; the Coinbase worker may not drop them silently or apply them to an older symbol/timeframe generation.
- Covering snapshots may replace older covering snapshots. A generation-matching incremental tail may replace or contiguously append to the last bar; if its covering snapshot is still pending, the publication slot merges that tail into the snapshot before delivery. Non-conflatable deltas, sequence gaps, and queue overflow require recovery rather than silent loss.
- Work is bounded by queue item/byte capacities, scheduler in-flight limits, cache bytes, segment bytes, chart bindings, handoffs, retries, and deadlines. No request creates an unbounded thread pool or unbounded queue.

Visible Coinbase history yields after each source-aware page: a continuation is appended only after the current page completes, so already-queued work for another series runs first within the eight-request provider lane. Selection and viewport changes set the request's cooperative cancellation token, which the production Coinbase adapter observes between pages, during pacing, and inside stop-aware transport operations. Coinbase requests retain a 30-second task deadline and five-second network-operation bound; the provider-history scheduler separately preserves the reusable per-instrument fairness and shared-interest contract for compositions that use it.

The production queue inventory is explicit:

- Authenticated engine clients and provider workers submit to the single coordinator through a 64-command channel. Coinbase and Rithmic history each have an eight-request provider queue, storage has 16 requests, and catalog command/event queues have 64 items. Producers use bounded submission; saturation returns a stage-specific error or degraded state, obsolete demand is cancelled or replaced by its generation, and no provider delta is conflated in these queues.
- Coinbase and Rithmic realtime workers each publish through a 2,048-event channel and retain at most 4,096 handoff items while history is installing. Submission is nonblocking. A full queue or handoff invalidates the provider generation and requires a covering history recovery; correctness-critical deltas are never silently dropped. Separate capacity-one control channels keep start, stop, and selection traffic independent of data saturation.
- Rithmic provider callbacks retain at most 256 items and 8 MiB per event/catalog lane; overflow latches a terminal generation event and retry instead of blocking the provider callback. The environment lane and provider-session command lane each hold eight items. Catalog results may be replaced only through newer generation-qualified demand; market events require recovery after loss.
- Desktop engine and Rithmic clients have 32-message publication mailboxes plus a bounded eight-message control reserve, and command capacities of 32 and eight respectively; the legacy presentation bridge has a capacity-one history command lane. Only market publications and diagnostics conflate: ordering-sensitive controls such as recovery, state, connection, catalog, selection markers, and viewport requests remain in FIFO order. When publication pressure overflows the base lane, queued publications may be replaced or fenced while controls remain intact; the bounded control reserve is never unbounded. A live tail mutates an unconsumed matching covering snapshot in place or replaces the prior pending tail. A non-conflatable overflow fences the generation and requests a covering snapshot. If event-slot conflation makes the next desktop tail non-contiguous, the application model preserves its last immutable generation and the engine client automatically requests and publishes a covering snapshot for that pane's exact series instead of making the chart terminally unavailable. The desktop mailbox raises one edge-triggered wake until drained; the foreground wake schedules the terminal's `FramePollGate` directly, which permits one pending active-window frame poll, and the chart bridge merges its bounded updates at that boundary without an extra workspace-to-shell wake. Coinbase application models retain the engine's bounded 32,768-bar working window; Rithmic presentation retains 600 items.
- Shutdown, DNS, native network/power wakeups, and request/reply rendezvous use dedicated capacity-one channels. Wakeups conflate because one pending notification represents the current native state; replies and lifecycle control do not conflate. Separate control channels, cancellation flags, and nonblocking producer paths prevent a full data queue from blocking the only consumer that can drain it.

Shared locks are limited to ownership handoff rather than market coordination. `EngineState` owns the workspace mutex for short authenticated mutations and persistence; `MarketRuntime` owns a shutdown-only worker-handle mutex; the Coinbase catalog boundary owns a short bounded consumer-authorization/result mutex so remove and detach invalidate queued work synchronously; desktop mailboxes own short queue, coalescing, result-slot, and waker mutexes; the native credential vault serializes platform credential API access; and the Rithmic adapter owns short connection-abort, callback, catalog, timing, and command-slot mutexes. Guards are released before wakeups, joins, socket work, or another lock is acquired. No synchronous mutex guard crosses an async suspension, and the engine/provider/storage owners do not use async suspension in their locked paths. The coordinator itself uses message ownership and has no shared state lock.

Provider readiness and failure are explicitly scoped. The authenticated engine handshake and client attachment complete as soon as IPC and the coordinator are healthy; Coinbase, Rithmic, history, and realtime readiness advance independently afterward. Provider-state and provider-wide series-state publications enter only consumers currently demanding that provider. Coinbase disconnect recovery retains its covering history and existing consumer identities. A newer Rithmic session resets only its live handoff, retains the prior covering snapshot as usable `Partial` state, requests local/provider repair for the new generation, and replaces the snapshot only when validated covering history arrives. A malformed provider/session identity is provider-session scoped, while an aggregation or buffer failure with valid identity is instrument scoped: only matching cadence series leave `Live`, sibling instruments and the other provider remain online, and repair uses their existing demand rather than reconstructing desktop state. Same-generation covering history may remove or finalize only the forming tail; every overlapping completed bar must remain byte-for-byte equal, and a rejected repair preserves the current snapshot. Storage degradation remains a separate persistence state and cannot disconnect either provider; GPUI remains in another process and cannot corrupt coordinator state.

The current protocol is market-data and provider-control only. It contains no order placement, replacement, cancellation, flattening, position, or execution-report command. A conformance test rejects introducing execution messages into the market publication protocol; any future trading subsystem requires a separate non-conflatable control boundary and explicit safety design.

Complexity is kept observable rather than inferred. The audited production Rust footprint is 67,422 lines across the application and product-library packages under the repository's test-aware counting method, excluding dedicated tests/benchmarks, vendor material, and Nucleus Charts. The increase covers the engine-owned dynamic Coinbase catalog and lifecycle fencing, exact multi-product realtime demand, truthful calendar timeframes, viewport-driven segmented history, pre-publication cache reservation, protected physical-byte enforcement, and the final authorization/metadata/active-viewport safety fences; the same review deleted superseded latest-segment, derived-only quota, and duplicate persistence APIs. Repository conformance enforces a 67,500-line platform soft review threshold and a 2,550-line resident process/IPC shell threshold. All-target Clippy plus a narrow dead-code-suppression allowlist prevents retired private surfaces from accumulating. The production trait inventory is fixed at nine provider transport/runtime, credential/security, and deterministic-substitution boundaries; a conformance allowlist makes every added trait an explicit architectural decision instead of a speculative abstraction.

## Performance evidence and instrumentation

Always-on feed diagnostics count trades, quotes, depth updates, publications, gaps, duplicates, malformed messages, stale callbacks, overflows, UI conflation, queue occupancy, memory, and lifecycle state. Opt-in fixed histograms cover socket-to-decode, decode-to-canonical, canonical-to-model, model-to-UI, UI-to-frame, and frame-to-present boundaries without unbounded label cardinality.

Resident-engine stability is verified through deterministic accelerated lifecycle and market-demand churn, configurable native soak windows, sampled resource high-water marks, and clean bounded shutdown. Development and release qualification do not require an exact uninterrupted eight-hour run on a personal workstation. Longer production-like observations are optional supplemental evidence; duration alone never substitutes for bounds, plateau behavior, queue continuity, cancellation, or shutdown checks. The existing exact-eight-hour capture harness is retained only as an optional diagnostic tool.

Local-history failures are reported only as redacted persistence-stage state; the crate does not expose provider payloads, credentials, account text, or instrument text through errors or labels. Deterministic storage lifecycle and performance runners measure publication, warm reads, decoding, derivation, recovery, and quarantine behavior without adding a second runtime metrics owner.

Native event delivery may defer a production input subscriber to a later frame. The windowed benchmark therefore advances each real symbol-change, submit, catalog-installation, and timeframe-selection stage only after its exact bounded command arrives, and fails any stage that exceeds 120 frame callbacks instead of assuming same-stack delivery or bypassing the production callback.

## Data correctness

Every streamed view has a local series identity, session generation, publication generation, and source sequence. A selection change invalidates older work. Covering snapshots establish a known state; deltas are accepted only when their sequence and session continue that state. A new session requires a covering snapshot, and older sessions or publication generations are rejected. A detected gap, stale response, or provider reconnect requires recovery from a covering snapshot.

Application replay snapshots retain session generation, publication generation, source sequence, provenance, and checksum evidence as pure in-process values; they are not a second IPC protocol. Desktop-to-engine traffic uses only versioned `engine_protocol`, while Rithmic vendor protobuf remains isolated inside its adapter. Persisted workspace and encrypted history use separate versioned schemas.

History and live data meet at one explicit handoff boundary:

1. Determine local coverage.
2. Fetch only missing provider history within provider limits.
3. Validate and publish a covering ordered snapshot.
4. Buffer or sequence live events during hydration.
5. Admit only live events newer than the accepted history boundary.

Series readiness and persistence are independent protocol axes. An exact memory hit publishes immediately; compatible in-memory or retained local history may publish a generation-fenced `Partial` covering snapshot before provider repair; provider completion installs and publishes `Ready` while asynchronous encrypted persistence is still `Pending`; and persistence failure changes that axis to `Degraded` without removing usable memory state. Provider failure with no usable history terminates the demand as stage-specific `Failed` plus `DemandError`, while newer consumer generations supersede and fence obsolete work. Coinbase derivation uses canonical one-minute bars only to build supported coarser intervals, never the reverse. Coinbase and Rithmic live handoffs buffer bounded generation-fenced events until covering history establishes continuity, then admit only events newer than the accepted boundary and enter `Live`; overflow, gaps, or conflicts force covering recovery.

Provider connection health is a third independent, provider-generation-qualified axis: disconnected, connecting, online, recovering, or failed. Storage runs on one separate bounded worker, and coordinator reads/persistence submissions are nonblocking; a local-history read that exceeds two seconds degrades persistence and starts provider repair without waiting for the storage worker, while a late valid result may still publish safely. Degraded disk state cannot stop provider connection, heartbeat, aggregation, or in-memory publication. The headless engine suite requires no GPUI dependency or desktop process and covers cold canonical history, coarser derivation/cache reuse, BTC/ETH and interval churn, stale-generation rejection, stalled and unavailable storage, live progression, and explicit provider-unavailable termination.

Prices and quantities use fixed-point or provider-exact representations. Floating-point conversion is a presentation concern and must not become the source of stored or transmitted truth.

## Concurrency and backpressure

Provider sessions, resident-engine workers, and GPUI have distinct owners. Do not let the UI thread perform blocking network, disk, process, or shutdown work. Do not let background workers mutate GPUI state directly. Desktop window close moves each worker's bounded detach acknowledgement to the GPUI background executor; app quit awaits those tasks before any complete-engine request. Complete engine shutdown is authenticated and bounded by one two-second process deadline. It freezes persistent workspace mutation, writes the final hot-set manifest on a named one-shot worker, stops new IPC acceptance and market publication, cancels in-flight history and Coinbase realtime work, closes Rithmic worker controls, drains accepted local-history requests, joins the top-level market workers, and then waits for client sessions with any remaining time. Each Rithmic worker owns cancellation handles and join handles for its blocking native network/power helpers; dropping the worker's environment receiver first releases bounded sends, native cancellation unblocks OS waits, and helper joins complete before the Rithmic worker exits. A stuck or panicked flush/market worker or an expired client-session wait causes process failure before unconditional process termination.

Shared upstream lifetime is derived from the engine's bounded subscription registry, not from coordinator event slots or the total number of registered consumers. Every accepted series mutation atomically updates only that consumer's generation-fenced demand and its bars/trades/quotes/depth requirements; duplicate series demand coalesces into one shared record with an exact consumer reference count. Matching charts and DOM consumers reference one process-owned provider session; removing one retains that session while another subscription or the explicit markets-live hot-set policy still owns a handoff, and the final market reference releases the Coinbase WebSocket or idles the Rithmic trade/depth worker even if unrelated consumers remain. A newer per-consumer generation becomes authoritative before cleanup: the coordinator sets the existing atomic cancellation token for unobserved Coinbase or Rithmic history without joining the worker, begins the replacement path immediately, fences late publication, and does not report an intentional cancellation as provider recovery.

Desktop IPC is authenticated platform-local socket transport only. Each accepted client has an independent bounded server session and market publication remains pull-based. `PublicationManager` assigns monotonic per-consumer generations across foreground/background/warm transitions; suspending UI publication preserves the watermark, and foreground restoration issues a newer covering snapshot. The coordinator retains one latest slot per semantic publication class, merges safe tails into pending snapshots, and reports realtime overflow as a staged recovery error. Desktop resource-class commands use a bounded conflated latest-value slot rather than a lossy ordinary command queue. Hidden UI mailboxes atomically reject and discard market publications until foreground restoration, so a stale hidden tail cannot precede the covering snapshot. Dormant clients cannot starve other control or demand work.

Queues must be bounded and have semantics appropriate to their payload:

- covering state may replace older covering state;
- transient deltas may be conflated only when the resulting state is provably equivalent;
- gaps and dropped non-conflatable events trigger recovery;
- control commands and future order actions are never silently dropped.

The render loop is demand-driven. Streaming data may request presentation, but it must not keep the UI permanently busy, block input dispatch, or recreate expensive workers for ordinary selection changes.

## Performance contract

Performance work is accepted with evidence from release builds on representative hardware. Track at least startup time, time to first usable local state, history-to-live readiness, UI input latency while streaming, frame time, memory growth, reconnect time, queue depth, and p50/p95/p99 provider-to-presentation latency.

Prefer improvements in this order:

1. Remove unnecessary work and copies.
2. Fix ownership, batching, wakeups, and algorithms.
3. Reuse allocations and compact hot data.
4. Use an existing platform or dependency primitive.
5. Add platform-specific optimization only after portable code misses a measured target.

Never trade determinism, recoverability, security, or cross-platform correctness for a benchmark headline.
